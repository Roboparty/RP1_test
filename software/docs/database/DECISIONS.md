# 数据库需求决策记录

日期：2026-09-17
状态：数据库基线已确认，旧数据导入后置

## 基础设施

1. 新平台采用 PostgreSQL、InfluxDB、NAS 三存储分工。
2. 本轮只搭建新 PostgreSQL；新 InfluxDB 和新 NAS 后续接入。
3. PostgreSQL 16 使用完全独立的 Docker 实例、端口、数据卷和账号。
4. 本轮目标是当前电脑上的影子开发环境，不是生产部署。
5. 新工程位于 `rp1-reliability-platform/`。
6. 使用 FastAPI、SQLAlchemy 2、Psycopg 3 和 Alembic 作为后续服务与迁移栈。

## 标识和 schema

1. 内部关系使用 `bigint GENERATED ALWAYS AS IDENTITY`。
2. 跨 PostgreSQL、InfluxDB、NAS 和 API 使用 UUIDv7 `public_id`。
3. 人员继续使用 `asset_code`、`cycle_code`、`execution_code` 等业务编号。
4. 数据库拆为 `iam`、`catalog`、`test`、`reliability`、`health`、`integration`、`audit` 七个 schema。
5. 单公司、多场地，不实现 SaaS 多租户。

## 修改、审计和结论

1. 测试业务数据允许直接修改，不设置核验后冻结。
2. PostgreSQL 自动保存关键表修改前后值、操作人、请求号、时间和原因。
3. 审计日志不可修改或删除。
4. 业务记录不物理删除，使用作废、停用或退休状态。
5. 正式结论只保留当前业务记录；前端只展示修改后的当前结果。
6. 旧结论内容通过后台审计日志追溯，不建立前端可见的结论版本链。
7. 数据修改后日常结果目标在 5 秒内更新；批量处理允许异步重算。

## 角色与数据权限

1. 角色固定为查看者、测试执行人员、系统管理员。
2. 查看者只读授权 Campaign。
3. 测试执行人员在授权 Campaign 内拥有较大的业务新增、修改、作废、分类、配置等效和复核权限。
4. 系统管理员额外管理用户、数据源、安全配置并发布正式结论。
5. 数据范围主要按 Campaign 授权，并强制携带整机/模块类型。
6. 后端权限检查之外启用 PostgreSQL RLS。
7. PostgreSQL 业务写入必须经过后端 API；浏览器、采集器和设备不直接访问业务表。

## 旧数据迁移

1. 权威旧 PostgreSQL 位于 `10.43.16.186:5432`，但新系统不建立网络访问。
2. 后续只做一次性 dump 文件导入，不做增量同步。
3. 本轮先构建数据库，数据导入后续单独实施。
4. 不长期保存旧库 dump，不保留 `legacy_staging`。
5. 迁移业务数据，排除密码、会话、Token、在线缓存和临时队列。
6. 不迁移旧 InfluxDB 数据。
7. 不迁移旧 NAS 文件。
8. 旧汇总性能指标不用于新老化分析。
9. 旧测试时长计入页面统一的累计测试总时长，但不进入新 MTBF 有效暴露。
10. 前端不区分新旧测试时长；数据库内部保留来源。
11. 现有样品迁入后，累计测试总时长连续，但新 MTBF 和长期性能分析周期重新开始。

## 资产、配置和测试结构

1. 公共资产主表加整机/模块一对一子表。
2. 数据库约束阻止模块加入整机 Campaign/Population，反之亦然。
3. 真实装配关系单独记录，不自动合并时间或故障。
4. 生产批次、MTBF Population 和健康参考群体分开建模。
5. 同批次只是健康参考候选条件，不自动成为健康标准。
6. 配置变化保留快照，但默认继承原 MTBF Population，不清零。
7. 只有重大或未知变化进入配置等效审核；测试执行人员处理，系统管理员最终批准。
8. 长期 `TestCycle` 包含多次 `Execution`，每次执行包含多个 `Stage`。
9. 正常暂停、换班、程序重启和外部断电不自动结束长期周期。

## 时间、暴露和 MTBF

1. 统一保存 `source_time`、`received_at`、`normalized_time`。
2. 数据库存 UTC，页面按 Asia/Shanghai 显示。
3. 累计测试总时长、测试运行时长和 MTBF 有效暴露在数据库中分开建模。
4. MTBF 使用阶段级时间区间；历史只存在汇总时长时仅计入测试总时长。
5. 同一底层区间可进入多个 scope，但同一样品同一 scope 不重复累计重叠时间。
6. Stage 使用多个 mission tag；scope 使用版本化规则纳入或排除。
7. 相关故障阶段缺失时先计入整体 MTBF，专项 scope 等待归属。
8. 统计方法、置信参数和判定规则版本化，数据库不写死单一 MTBF 公式。
9. 正式计算保存输入摘要、输入哈希、方法版本和输出快照。

## 故障和中断

1. 一次中断最多贡献一次故障。
2. FAILED 必须关联已发布的正式错误码。
3. 未知内部错误先记 BLOCKED，并保留原始错误信息。
4. 外部断电、台架故障、外部网络和操作员停止记 NON_RELEVANT。
5. 同一中断可以关联一个主码和多个伴随码。
6. BLOCKED 转 FAILED 后实时重算；变更保留审计。

## 健康和长期性能

1. F0/F1/F2 策略支持时间、距离、步数、抓取、循环、电池循环和事件触发。
2. 多触发条件默认任一条件先到即到期，也允许全部满足模式。
3. InfluxDB 保存高频原始数据；PostgreSQL 保存标准化检查点和派生指标。
4. 指标使用标准单位计算，同时保存原始值、原始单位和转换方法。
5. 性能数据质量和 MTBF 暴露质量独立；性能缺失不取消可确认的 MTBF 时间。
6. 维修、换件或关键变化后完整长期曲线继续保留，并创建分析分段和事件标记。
7. 新分段不强制 F2 基线；没有正式基线时，使用变更后第一个有效点作为观察参考点。
8. 图表前后分段使用不同颜色并显示变更标记；数据库保存分段和参考点，不在前端重算事实。

## 接入、保留和备份

1. 采集端支持离线缓存和幂等补传。
2. 每条接入记录具有稳定幂等键、设备时间和序列信息。
3. 数据保留策略版本化；正式证据可被保护，不受普通清理影响。
4. 正式初始化不写假业务数据；演示数据使用独立脚本。
5. 只保留一份最新备份，成功的新备份原子覆盖上一份。
6. 新备份失败时保留上一份有效备份，并提供恢复验证脚本。
